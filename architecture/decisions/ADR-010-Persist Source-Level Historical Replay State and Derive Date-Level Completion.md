# ADR-010: Persist Source-Level Replay State and Support Partial Historical Replay Recovery

## Status

Accepted

## Date

2026-08-17

## Related Decisions

- ADR-007, ADR-008, ADR-009

---

## Context

ADR-009 introduced Mercury's historical replay architecture.

The platform can now coordinate:

```text
Source Delivery Provider
        ↓
SourceDeliveryBatch
        ↓
HistoricalReplayRunner
        ↓
Connectors
        ↓
Immutable GCS Raw Landing
        ↓
BigQueryRawLoader
        ↓
BigQuery Raw
```

For the current Olist incremental replay, one business date contains four expected source objects:

```text
orders
order_items
payments
reviews
```

These four source objects are orchestrated together because they belong to the same historical business date.

However, they do **not** represent one physical source.

They represent independent source deliveries that may ultimately originate from different platforms, APIs, credentials, schedules, and operational systems.

Conceptually:

```text
Order Platform
├── orders
└── order_items

Payment Platform
└── payments

Review Platform
└── reviews
```

Grouping these sources into one daily replay must therefore not erase their operational independence.

---

## Problem

The initial ADR-009 implementation intentionally used conservative failure behavior while historical replay was being proven.

This was appropriate because Mercury first needed to validate:

- source simulation;
- source delivery abstraction;
- connector execution;
- immutable GCS Raw landing;
- BigQuery loading;
- partition routing;
- historical date iteration;
- real GCP integration.

Once the end-to-end replay was successfully validated, a more important operational problem became visible.

A long historical replay may partially succeed.

For example:

```text
2017-05-12

orders       succeeded
order_items  succeeded
payments     failed
reviews      succeeded
```

Mercury needs to know:

- exactly which source failed;
- where it failed;
- which sources successfully completed;
- which data is already safely available;
- whether the business date is complete;
- which replay invocation produced the outcome;
- what work should eventually be eligible for targeted recovery.

A single date-level status such as:

```text
2017-05-12 | FAILED
```

is insufficient.

It loses the operational distinction between independent sources.

---

# Decision

Mercury will persist historical replay state at the:

```text
delivery_date + source_object
```

grain.

Each source will be observed independently.

Each state transition will be stored as an **append-only replay event**.

Mercury will derive date-level completeness from the latest source-level states.

Mercury will also distinguish:

```text
source availability
```

from:

```text
date completeness
```

Successfully processed independent source data may become available in BigQuery even when another source for the same date fails.

The overall date remains incomplete until every expected source has completed successfully.

---

# Replay Identity Model

Mercury uses three different identities for replay metadata.

## run_id

`run_id` identifies one top-level replay execution attempt.

For example:

```python
run_range(
    start_date=date(2017, 5, 12),
    end_date=date(2017, 5, 15),
)
```

receives one `run_id`.

Every replay-state event generated by that invocation shares the same `run_id`.

A later replay or recovery attempt receives a different `run_id`.

A standalone:

```python
run_day(...)
```

also receives its own `run_id`.

Conceptually:

```text
run_id
→ which replay execution attempt produced this event?
```

---

## event_id

Each append-only state transition has a unique `event_id`.

For example:

```text
RUNNING | INGESTION
RUNNING | WAREHOUSE
SUCCESS | WAREHOUSE
```

are three different events and therefore have three different `event_id` values.

Conceptually:

```text
event_id
→ which individual state transition is this?
```

---

## Logical Source Identity

The logical source delivery remains:

```text
(delivery_date, source_object)
```

For example:

```text
(2017-05-12, payments)
```

identifies the Payments delivery for that business date regardless of how many attempts or state events exist.

Therefore:

```text
run_id
    → replay attempt

event_id
    → individual state transition

delivery_date + source_object
    → logical source delivery
```

These identities are complementary and must not be conflated.

---

# Append-Only Replay History

Replay state is append-only.

Mercury does not overwrite one mutable row for:

```text
(delivery_date, source_object)
```

Instead, every state transition is preserved.

For example:

```text
run A | payments | RUNNING | INGESTION
run A | payments | FAILED  | INGESTION
```

and a later recovery attempt may produce:

```text
run B | payments | RUNNING | INGESTION
run B | payments | RUNNING | WAREHOUSE
run B | payments | SUCCESS | WAREHOUSE
```

Both histories remain available.

The latest event represents the current known state of the logical source delivery.

This provides:

- auditability;
- debugging history;
- visibility into previous failures;
- future retry/recovery traceability;
- protection against destructive state updates.

---

# Replay Status

Mercury defines three source-level replay statuses:

```text
RUNNING
SUCCESS
FAILED
```

There is no persisted `NOT_RUN` state.

If no event exists for a logical source delivery, that source has not been attempted.

---

# Replay Stages

Mercury defines the following orchestration stages:

```text
SOURCE_DELIVERY
INGESTION
WAREHOUSE
```

These correspond to the primary replay boundaries.

---

# SOURCE_DELIVERY Stage

`SOURCE_DELIVERY` represents acquisition of source data from an upstream provider.

The current Olist implementation obtains the full daily `SourceDeliveryBatch` through one provider operation.

If that provider fails before a valid batch is returned, Mercury cannot necessarily determine which individual source object caused the provider failure.

Therefore Mercury must not fabricate source-specific `SOURCE_DELIVERY` events when source attribution is unknown.

For the current Olist replay, source-level state tracking begins after a valid daily batch has been obtained and validated.

The `SOURCE_DELIVERY` stage remains part of the generic state model because future providers may obtain sources independently.

For example:

```text
Orders API
Payments API
Reviews API
```

could later produce independently attributable source-delivery state.

---

# SUCCESS Semantics

`SUCCESS` has exactly one meaning:

> The individual source successfully completed its required end-to-end replay path through BigQuery Raw.

Therefore the only valid successful terminal state is:

```text
SUCCESS | WAREHOUSE
```

Mercury does not persist:

```text
SUCCESS | SOURCE_DELIVERY
SUCCESS | INGESTION
```

Intermediate progress is represented by entering the next stage.

The valid status/stage combinations are:

```text
RUNNING | SOURCE_DELIVERY
RUNNING | INGESTION
RUNNING | WAREHOUSE

FAILED  | SOURCE_DELIVERY
FAILED  | INGESTION
FAILED  | WAREHOUSE

SUCCESS | WAREHOUSE
```

This invariant is enforced by the replay-state domain model.

---

# ReplayStateRecord

Each append-only replay-state event contains at minimum:

```text
run_id
event_id
delivery_date
source_object
status
stage
started_at
completed_at
error_message
recorded_at
```

All timestamps are timezone-aware.

UTC is used for persisted operational timestamps.

---

# started_at Semantics

For one logical source execution attempt, `started_at` represents the beginning of that source's execution during the current replay attempt.

The same source-execution start time may therefore be associated with its subsequent state transitions.

For example:

```text
payments | RUNNING | INGESTION
payments | RUNNING | WAREHOUSE
payments | SUCCESS | WAREHOUSE
```

belong to the same source execution attempt.

`recorded_at` identifies when each individual event was persisted.

`completed_at` is present only for terminal `FAILED` or `SUCCESS` states.

---

# ReplayStateStore

Mercury introduces a generic:

```text
ReplayStateStore
```

abstraction.

The state store is responsible for durable operational state.

Its core contract supports:

```text
append(record)

get_history(delivery_date, source_object)

get_latest(delivery_date, source_object)

get_latest_for_date(delivery_date)
```

The contract contains no BigQuery-specific concepts.

It must not expose:

```text
project_id
dataset_id
table_id
SQL
BigQuery jobs
```

These belong to concrete persistence adapters.

---

# BigQueryReplayStateStore

Mercury uses:

```text
BigQueryReplayStateStore
```

as the initial persistent state-store implementation.

It writes operational metadata into a dedicated BigQuery metadata dataset.

Replay state must not be stored in the `raw` dataset.

The intended platform separation is:

```text
raw
└── source-faithful Raw data

metadata
└── platform execution and operational metadata
```

The initial replay-state table is:

```text
metadata.historical_replay_state
```

---

# BigQuery Replay-State Schema

The replay-state table uses an explicit schema:

```text
run_id          STRING       REQUIRED
event_id        STRING       REQUIRED
delivery_date   DATE         REQUIRED
source_object   STRING       REQUIRED
status          STRING       REQUIRED
stage           STRING       REQUIRED
started_at      TIMESTAMP    REQUIRED
completed_at    TIMESTAMP    NULLABLE
error_message   STRING       NULLABLE
recorded_at     TIMESTAMP    REQUIRED
```

Schema autodetection is not used.

Enum values are persisted as their plain string values.

---

# Metadata Partitioning and Clustering

The replay-state table is partitioned by:

```text
delivery_date
```

using DAY partitioning.

This reflects the primary historical-replay query pattern.

The table is clustered by:

```text
source_object
```

because operational queries frequently combine:

```text
delivery_date
+
source_object
```

---

# Resource Initialization

BigQuery metadata resources are created explicitly through the BigQuery-backed state store.

Construction of `BigQueryReplayStateStore` must not unexpectedly provision infrastructure.

Resource creation therefore occurs through an explicit operation such as:

```text
ensure_resources()
```

Dataset and table creation are idempotent.

Existing resources are not deleted or recreated.

`HistoricalReplayRunner` depends only on the generic `ReplayStateStore` contract and therefore does not call BigQuery-specific provisioning methods.

Infrastructure initialization remains outside the runner.

---

# Daily Replay Execution Model

A daily replay remains one date-level orchestration unit.

However, the sources inside the date are independently executed and observed.

Mercury uses two ordered execution phases:

```text
SourceDeliveryBatch
        |
        v
validate complete expected membership
        |
        v
+---------------------------+
|     INGESTION PHASE       |
|                           |
| attempt every expected    |
| independent source        |
+-------------+-------------+
              |
              v
       collect individual
       connector outcomes
              |
              v
+---------------------------+
|      WAREHOUSE PHASE      |
|                           |
| load every source whose   |
| ingestion succeeded       |
+-------------+-------------+
              |
              v
    derive date completeness
```

Mercury completes all ingestion attempts before entering the warehouse phase.

It does **not** interleave:

```text
orders ingestion
orders warehouse
payments ingestion
payments warehouse
...
```

Stage separation remains intentional.

---

# Why Stage Separation Is Preserved

Stage separation makes the execution state easier to reason about.

After the ingestion phase Mercury can clearly determine:

```text
which sources landed successfully
which sources failed ingestion
which immutable GCS artifacts exist
```

Only then does warehouse loading begin.

This gives Mercury a clear operational boundary:

```text
source acquisition
        ↓
Raw landing
        ↓
warehouse loading
```

without requiring every source to succeed before useful data may progress.

---

# Ingestion Phase

For each expected source, Mercury records:

```text
RUNNING | INGESTION
```

before its connector execution begins.

The existing connector remains responsible for:

- source validation;
- connector-specific behavior;
- ingestion metadata;
- Raw landing through the configured `StorageManager`.

All expected source connectors for the date are attempted.

Mercury does not stop attempting the remaining independent sources because an earlier source failed.

For example:

```text
orders       → succeeded
order_items  → succeeded
payments     → failed
reviews      → succeeded
```

is a valid partial ingestion outcome.

This provides both:

- maximum safe source availability;
- complete source-level diagnostic information.

---

# Ingestion Failure

If ingestion for one source fails, Mercury records:

```text
FAILED | INGESTION
```

for that source.

The failure metadata includes the available error information.

That source is not eligible for warehouse loading.

However, the failure does not stop other expected source connectors for the same date from being attempted.

Therefore:

```text
payments failed
```

does not automatically imply:

```text
reviews not attempted
```

when Reviews is an independent source.

---

# Ingestion Success

Mercury does not record:

```text
SUCCESS | INGESTION
```

Successful ingestion is represented by the source becoming eligible for the next stage.

The next state transition is:

```text
RUNNING | WAREHOUSE
```

when warehouse loading begins.

---

# Warehouse Eligibility

After all expected ingestion attempts have completed, Mercury determines which sources are warehouse-eligible.

A source is eligible only when its ingestion completed successfully and produced a valid landed Raw artifact.

For example:

```text
INGESTION

orders       succeeded
order_items  succeeded
payments     failed
reviews      succeeded
```

produces:

```text
WAREHOUSE ELIGIBILITY

orders       eligible
order_items  eligible
payments     not eligible
reviews      eligible
```

Mercury does not fabricate a warehouse failure for Payments.

Warehouse was never attempted for that source.

Its latest state remains:

```text
FAILED | INGESTION
```

---

# Warehouse Phase

Before a BigQuery Raw load begins for an eligible source, Mercury records:

```text
RUNNING | WAREHOUSE
```

The existing `BigQueryRawLoader` is then called using the landing path produced by connector ingestion metadata.

The orchestration layer does not reconstruct GCS paths.

---

# Warehouse Success

Only after the BigQuery load succeeds does Mercury record:

```text
SUCCESS | WAREHOUSE
```

This means the source completed:

```text
source available
        ↓
connector validation
        ↓
GCS Raw landing
        ↓
BigQuery Raw loading
        ↓
SUCCESS
```

---

# Warehouse Failure

If BigQuery loading fails for one source, Mercury records:

```text
FAILED | WAREHOUSE
```

The existing GCS artifact remains untouched.

Mercury does not:

- delete the GCS artifact;
- delete successful BigQuery data;
- roll back unrelated source loads;
- overwrite Raw data;
- hide the failure.

A warehouse failure for one source does not prevent the other eligible independent sources for the same date from being attempted.

---

# Attempt-All-Safe-Work Within a Date

Within one business date, Mercury follows:

```text
attempt-all-safe-work
```

semantics.

Suppose the date produces:

```text
orders
    ingestion succeeded
    warehouse succeeded

order_items
    ingestion succeeded
    warehouse succeeded

payments
    ingestion failed

reviews
    ingestion succeeded
    warehouse succeeded
```

The resulting latest replay states are:

```text
orders       SUCCESS | WAREHOUSE
order_items  SUCCESS | WAREHOUSE
payments     FAILED  | INGESTION
reviews      SUCCESS | WAREHOUSE
```

The resulting BigQuery availability is:

```text
orders       available
order_items  available
payments     unavailable
reviews      available
```

This is intentional.

Mercury does not withhold valid independent source data merely because another source failed.

---

# Availability vs Completeness

Mercury explicitly separates:

```text
source availability
```

from:

```text
date completeness
```

Therefore:

```text
source availability != date completeness
```

A source may be successfully available even when the complete business date is not.

This reflects real platform usage.

For example:

```text
Sales-volume dashboard
    → may require orders only

Review analytics
    → may require reviews only

Revenue reconciliation
    → may require orders + payments
```

If the Payment Platform is temporarily unavailable, Mercury should not unnecessarily prevent an Orders-only downstream product from receiving valid Orders data.

Downstream dependency requirements are not determined by the Raw replay layer.

The platform exposes valid source data and separately exposes completeness information.

---

# Date-Level Completion

Date-level completeness is derived.

It is not stored as a separate mutable status row.

For the current Olist incremental replay, the expected source set is:

```text
orders
order_items
payments
reviews
```

Mercury queries the latest source-level state for the date.

A date is complete only when:

1. all expected source objects are represented;
2. no unexpected source objects are present in the state set being evaluated;
3. all records belong to the same delivery date;
4. every expected source's latest state is:

```text
SUCCESS | WAREHOUSE
```

Conceptually:

```text
orders       SUCCESS
order_items  SUCCESS
payments     SUCCESS
reviews      SUCCESS
-------------------------
DATE         COMPLETE
```

If any source is:

```text
missing
RUNNING
FAILED
```

then:

```text
DATE         INCOMPLETE
```

---

# is_date_complete()

Mercury uses a pure domain helper such as:

```text
is_date_complete()
```

to derive date completeness.

The function operates on current/latest source states.

It returns `False` for valid but incomplete state, including:

- missing expected source;
- failed source;
- running source;
- unexpected source.

Malformed caller input is rejected rather than silently interpreted.

For example, records from multiple delivery dates are invalid input and raise an error.

This distinguishes:

```text
valid incomplete state
```

from:

```text
invalid state evaluation
```

---

# Range-Level Execution

Within a date Mercury attempts all safe work.

Across dates, Mercury remains conservative.

The historical replay rule is:

```text
process current date
        ↓
attempt all ingestion
        ↓
warehouse all eligible sources
        ↓
derive completeness
        ↓
COMPLETE?
   /       \
 yes       no
  |         |
next      stop
date      range
```

For example:

```text
2017-05-12  COMPLETE
2017-05-13  COMPLETE
2017-05-14  INCOMPLETE
2017-05-15  NOT ATTEMPTED
```

Mercury therefore maximizes safe availability for the incomplete date without automatically extending a known historical completeness gap farther into the requested range.

---

# run_id Across a Range

One call to:

```python
run_range(...)
```

generates exactly one `run_id`.

That identifier is shared by every replay-state event generated by every attempted date in that range invocation.

For example:

```text
run_id = A

May 12 orders
May 12 payments
May 13 orders
May 13 reviews
May 14 payments failure
```

all belong to run A.

If the operator later starts another replay or recovery attempt:

```text
run_id = B
```

is generated.

This makes separate attempts auditable.

---

# Standalone run_day()

A standalone call to:

```python
run_day(...)
```

receives its own `run_id`.

The public caller does not need to generate or manage replay IDs manually.

Run identity belongs to orchestration.

Internally, `run_range()` may delegate to a private day-execution method while preserving the range's shared `run_id`.

---

# Initial / Reference Loads

ADR-010 primarily addresses incremental historical replay.

The initial/reference workflow:

```text
customers
products
sellers
geolocations
```

is currently a one-off load rather than a multi-date historical replay.

Source-level recovery tracking for the initial/reference workflow is not required by this ADR's initial implementation.

`run_initial_load()` may therefore remain unchanged unless a later operational requirement explicitly extends replay-state tracking to reference loads.

---

# Connector Metadata vs Replay State

Connector metadata and replay state serve different purposes.

Connector metadata describes ingestion details such as:

```text
ingestion_id
source_system
source_object
source_file_name
started_at
completed_at
landing_path
file_size
checksum
record_count
status
error_message
schema_version
```

Replay state describes orchestration progress:

```text
run_id
delivery_date
source_object
status
stage
```

Mercury must not unnecessarily copy every connector metadata field into the replay-state table.

The existing `ConnectorRunResult` remains the source of ingestion-level detail.

Replay state provides orchestration-level visibility.

These two metadata models complement rather than replace one another.

---

# State Persistence Failure

Replay state is part of Mercury's control plane.

If Mercury cannot persist required replay state, it must not silently continue as though observability remains reliable.

For example, if writing:

```text
RUNNING | INGESTION
```

fails before a connector begins, the connector must not run.

If ingestion has succeeded but writing:

```text
RUNNING | WAREHOUSE
```

fails, BigQuery loading must not begin for that source.

If BigQuery succeeds but persisting:

```text
SUCCESS | WAREHOUSE
```

fails, Mercury must surface the state-store failure.

It must not roll back:

- the immutable GCS object;
- the successful BigQuery load.

This represents a partial control-plane failure and must remain visible for future reconciliation/recovery design.

State persistence is therefore not treated as optional best-effort logging.

---

# Provider Failure

If:

```text
SourceDeliveryProvider.get_daily_delivery(...)
```

fails before a valid source-delivery batch exists, Mercury cannot safely attribute the failure to a specific source object.

In that case:

- the provider failure propagates;
- no fabricated per-source state events are written;
- connector execution does not begin;
- warehouse loading does not begin.

Future independently observable source providers may allow source-level `SOURCE_DELIVERY` state to be persisted.

---

# Current-State Derivation Across Runs

Replay history may contain multiple attempts.

For example:

```text
run A | payments | FAILED  | INGESTION
run B | payments | SUCCESS | WAREHOUSE
```

Current state is derived from the latest recorded state for the logical source delivery.

Therefore the current Payments state is:

```text
SUCCESS | WAREHOUSE
```

while the earlier failure remains visible in history.

The append-only model preserves both operational truth and current-state derivation.

---

# Recovery Direction

Persisted source-level state makes targeted recovery possible.

Suppose:

```text
run A

orders       SUCCESS | WAREHOUSE
order_items  SUCCESS | WAREHOUSE
payments     FAILED  | INGESTION
reviews      SUCCESS | WAREHOUSE
```

The date is incomplete.

A future targeted recovery should be able to operate on:

```text
payments
```

without unnecessarily rerunning:

```text
orders
order_items
reviews
```

A later attempt may produce:

```text
run B

payments     RUNNING | INGESTION
payments     RUNNING | WAREHOUSE
payments     SUCCESS | WAREHOUSE
```

The latest states then become:

```text
orders       SUCCESS
order_items  SUCCESS
payments     SUCCESS
reviews      SUCCESS
```

and the date becomes complete.

This is the intended recovery direction.

---

# Recovery Safety

Replay state tells Mercury **what happened**.

It does not automatically mean every failed operation can simply be repeated from the beginning.

Recovery logic must consider the failure stage.

For example:

## Failed During Ingestion Before GCS Landing

A future recovery may need to rerun the connector.

## Failed After GCS Landing but Before Warehouse Completion

The immutable Raw artifact may already exist.

Recovery should therefore avoid blindly rerunning ingestion if doing so would collide with the existing immutable GCS destination.

## Failed During Warehouse Loading

The correct recovery may be to reuse the existing GCS artifact and retry only the warehouse stage.

## Warehouse Succeeded but SUCCESS State Persistence Failed

The data may already exist correctly in BigQuery even though replay metadata does not yet reflect that success.

This requires reconciliation rather than destructive reprocessing.

Therefore recovery actions must remain stage-aware.

---

# No Automatic Destructive Recovery

ADR-010 does not permit recovery logic to weaken Raw immutability.

Recovery must not introduce:

```text
force=True
overwrite=True
delete-and-reload by default
```

behavior merely to make retry logic convenient.

Existing Raw artifacts remain immutable.

Existing successfully loaded independent sources remain preserved.

---

# Retry Policy

Automatic network retry/backoff behavior is not introduced by this ADR.

Before automatic retries are added, Mercury must distinguish which operations are safely idempotent and which require reconciliation.

Examples include:

- provider acquisition;
- GCS create-only landing;
- BigQuery partition replacement;
- replay-state append operations.

Automatic retry strategy may be introduced separately after these semantics are explicit.

---

# Recovery Scope

ADR-010 establishes the operational state and execution semantics required for targeted source recovery.

The intended recovery model is:

```text
identify incomplete date
        ↓
inspect latest source states
        ↓
identify failed/incomplete sources
        ↓
determine failure stage
        ↓
perform only safe required work
        ↓
append new state under new run_id
        ↓
derive date completeness again
```

Recovery must not unnecessarily rerun already successful independent sources.

The exact public recovery API may be introduced during implementation or in a subsequent narrowly scoped decision once stage-aware recovery behavior is finalized.

---

# ReplayStateStore Provider Independence

Replay-state persistence belongs to orchestration, not source acquisition.

`OlistSimulatedSourceProvider` must not manage replay state.

Likewise a future:

```text
RestApiSourceProvider
```

must not require changes to the generic replay-state model.

The intended dependency direction is:

```text
SourceDeliveryProvider
        ↓
HistoricalReplayRunner
        ↓
ReplayStateStore
```

not:

```text
Olist simulator
        ↓
Olist-specific state database
```

This preserves ADR-009's provider abstraction.

---

# Separation of Responsibilities

## SourceDeliveryProvider

Responsible for:

```text
making source deliveries available
```

Not responsible for:

- Raw landing;
- BigQuery loading;
- replay-state persistence;
- recovery decisions.

---

## Connector / Ingestion Layer

Responsible for:

```text
source validation
ingestion metadata
Raw landing
```

Not responsible for:

- date completeness;
- replay range progression;
- replay-state queries;
- recovery orchestration.

---

## BigQueryRawLoader

Responsible for:

```text
loading successfully landed Raw artifacts into BigQuery Raw
```

Not responsible for:

- replay-state persistence;
- source completeness;
- retry decisions.

---

## HistoricalReplayRunner

Responsible for:

```text
daily orchestration
expected-source validation
ingestion-phase execution
warehouse eligibility
warehouse-phase execution
state transition recording
date-completeness derivation
range progression/stopping
```

It depends on the generic `ReplayStateStore`.

---

## ReplayStateStore

Responsible for:

```text
durable append-only source-level replay history
latest-state retrieval
date-level state retrieval
```

It does not execute ingestion or warehouse operations.

---

## BigQueryReplayStateStore

Responsible for:

```text
persisting ReplayStateRecord objects in BigQuery metadata
querying replay history
querying latest source state
```

It does not know about:

- connectors;
- Olist;
- GCS;
- BigQuery Raw loading;
- replay range logic.

---

# Alternatives Considered

## Date-Level State Only

Example:

```text
2017-05-12 | FAILED
```

Rejected.

This loses:

- which source failed;
- failure stage;
- which sources remain usable;
- information required for targeted recovery.

---

## Treat All Daily Sources as One Physical Source

Rejected.

The sources may represent independent platforms and APIs.

Daily orchestration does not imply source identity.

---

## All-or-Nothing Warehouse Gate

Require all four source ingestions to succeed before any BigQuery load begins.

Initially useful as a conservative orchestration model.

Rejected as the final production-oriented behavior because one independent source failure would unnecessarily withhold valid data from unrelated successful sources.

---

## Stop at First Failed Source Within a Date

Rejected.

A failure in one independent source should not prevent Mercury from learning the state of or making available other safe sources for the same date.

Mercury therefore attempts all expected ingestion sources and all independently eligible warehouse loads.

---

## End-to-End Source-by-Source Interleaving

Example:

```text
orders       ingestion → warehouse
order_items  ingestion → warehouse
payments     ingestion → warehouse
reviews      ingestion → warehouse
```

Rejected as the preferred model.

Mercury preserves clean stage boundaries:

```text
all ingestion attempts
        ↓
warehouse eligible sources
```

This makes operational reasoning and recovery simpler.

---

## Persist Date COMPLETE / INCOMPLETE Rows

Rejected.

Date completeness is derived from source-level latest state.

Persisting it separately would create two mutable representations of the same truth.

---

## Infer Replay State from GCS

Rejected.

GCS existence proves Raw landing but does not prove BigQuery success.

---

## Infer Replay State from BigQuery

Rejected.

BigQuery availability does not explain source-delivery or ingestion failures and does not preserve full execution history.

---

## Store Replay Metadata in Raw

Rejected.

Replay state is operational platform metadata, not source data.

---

## Mutable Upsert State Table

Rejected.

Updating one row per logical source would destroy transition history and retry visibility.

Append-only events are preferred.

---

## Automatically Retry Everything

Rejected.

Failure-stage differences mean blindly retrying all operations may violate immutability or repeat unnecessary work.

Recovery must be stage-aware.

# Consequences

## Positive

Mercury gains durable source-level operational history.

Independent sources remain observable.

Partial source availability is supported.

A single failing source no longer unnecessarily blocks unrelated successfully processed data for the same date.

Date completeness remains explicit.

Historical range progression remains conservative after an incomplete date.

Failures can be associated with the correct stage.

Replay attempts can be correlated through `run_id`.

Individual transitions can be identified through `event_id`.

Past failures remain auditable after successful recovery.

The architecture supports future API-based independent sources.

The metadata provides the information required for targeted recovery.

Raw immutability remains intact.

---

## Negative

Historical replay becomes operationally more complex.

A BigQuery date may intentionally contain only some source partitions/tables.

Downstream consumers cannot assume that one available source means the full date is complete.

Replay-state persistence becomes part of the control plane and therefore another dependency that can itself fail.

Recovery requires stage-aware logic.

The append-only state table grows with each transition and recovery attempt.

Operational tooling will eventually be needed to make replay status easy to inspect.

---

# Validation Requirements

The completed implementation must prove at minimum:

1. `run_id` is persisted with every replay event;
2. one range invocation shares one `run_id`;
3. separate replay invocations use different `run_id` values;
4. every event has a unique `event_id`;
5. source state is tracked independently;
6. `RUNNING | INGESTION` is written before connector execution;
7. ingestion failures produce `FAILED | INGESTION`;
8. one ingestion failure does not prevent other expected source ingestion attempts for the same date;
9. only successfully ingested sources enter the warehouse phase;
10. `RUNNING | WAREHOUSE` is written before BigQuery loading;
11. warehouse success produces `SUCCESS | WAREHOUSE`;
12. warehouse failure produces `FAILED | WAREHOUSE`;
13. one warehouse failure does not prevent other eligible source warehouse attempts for the same date;
14. successfully processed independent data remains available;
15. date completeness is derived only after all safe work for the date is attempted;
16. incomplete date stops later dates in the historical range;
17. provider failure before a batch exists does not fabricate per-source state;
18. state-store failure is not silently ignored;
19. replay state does not weaken GCS immutability;
20. replay state does not change existing Raw schema/loading rules;
21. existing connector metadata remains available;
22. all automated tests remain offline;
23. all existing tests continue to pass.

# Implementation Direction

Implementation proceeds in phases.

## Phase 1 — Replay-State Foundation

Implemented:

```text
ReplayStatus
ReplayStage
ReplayStateRecord
ReplayStateStore
BigQueryReplayStateStore
is_date_complete()
```

Replay state is append-only.

`SUCCESS` is warehouse-only.

BigQuery metadata resources remain separate from Raw.

---

## Phase 2 — Runner Integration

The historical replay runner is extended with:

```text
ReplayStateStore dependency
run_id generation
source-level state events
attempt-all-safe-work semantics
partial source availability
derived date completeness
range stopping after incomplete date
```

The existing provider, connectors, storage implementations, and `BigQueryRawLoader` remain responsible for their existing concerns.

---

## Phase 3 — Targeted Recovery

Using the state produced by Phases 1 and 2, Mercury can implement stage-aware recovery.

Recovery should:

```text
inspect incomplete date
        ↓
inspect latest source states
        ↓
identify only failed/incomplete sources
        ↓
determine required recovery stage
        ↓
reuse existing immutable artifacts where appropriate
        ↓
append new events under a new run_id
        ↓
derive completeness again
```

Phase 3 must not unnecessarily rerun already successful sources.

---

# Final Decision

Mercury will persist append-only historical replay state at the source-object and delivery-date grain.

Each replay invocation receives a `run_id`.

Each state transition receives an `event_id`.

Sources remain independently observable even when orchestrated as one daily batch.

Mercury executes daily replay in two ordered phases:

```text
attempt all expected source ingestions
        ↓
warehouse every successfully ingested source
        ↓
derive date completeness
```

A failure in one source does not prevent unrelated safe work for the same date.

Successfully processed independent source data may become available even when the overall business date is incomplete.

Date completeness is derived only when all expected sources have reached:

```text
SUCCESS | WAREHOUSE
```

An incomplete date stops automatic progression to later historical dates after all safe work for the current date has been attempted.

Replay state is stored as operational metadata outside the Raw layer.

Existing immutable GCS behavior is preserved.

Recovery will use source-level state and failure-stage information to target only the work that actually requires recovery rather than blindly rerunning already successful sources.

The governing principles are:

> Source availability and date completeness are separate concepts.

> Maximize safe source availability without misrepresenting completeness.

> Persist what happened before automating recovery from what happened.

> Recover only the work that requires recovery while preserving immutable successful work.
